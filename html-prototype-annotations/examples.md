# 业务标注文案范例

以下为**通用**写法，具体按钮文案、步骤名称以当前页面为准。

## 好的描述

**底部主操作栏**
> 驱动主流程：各步骤的主按钮（如「下一步」「提交」「返回」）；异步任务进行中时隐藏或禁用，避免重复提交。

**可选能力**
> 可选：上传附件后系统自动解析并填入列表；也可跳过，改为手工录入。

**原型限制如实说明**
> 展示服务协议勾选框，用于确认用户已知悉条款（**本原型仅作展示，未做勾选校验**）。

**统计卡片交互准确**
> 展示总数、成功数、失败数等汇总；可点击的卡片写清「点击 xx 卡片可筛选下方列表」；**不可点击**的纯展示项不要写「点击筛选」。

## 应修正的描述

| 问题 | 错误 | 正确 |
|------|------|------|
| 技术用语 | 「Hero 区说明能力」 | 「顶部说明区介绍…」 |
| 演示开关 | 「可切换 UI 方案」 | 「展示成功/失败/超时等结果态」 |
| 按钮文案不符 | 与页面不一致的链接/按钮名 | 与界面**完全一致**的实际文案 |
| 交互不存在 | 描述未实现的点击区域 | 只写真实存在的入口（按钮、链接） |
| 导出入口混淆 | 一个按钮写多种导出 | 每个导出入口单独一条，各写各的范围 |
| 必做误导 | 「必须完成 xx 才能继续」 | 若为选填，写「可选，可跳过」 |

## 新增标注检查单

写每条 `desc` 前确认：

1. 界面上该区域的**实际按钮/链接文案**是什么？
2. 功能是必选还是选填？原型是否做了校验？
3. 有没有仅用于原型演示的状态切换（不写进业务说明，或评审时口头补充）？
4. 弹窗内能力是否单独成条，还是合并进入口按钮描述？
5. 读给非技术人员听，是否还需要解释技术术语？

## 分组建议

| group | 典型内容 |
|-------|----------|
| `global` | 页头、步骤条、侧栏、底部栏 |
| 步骤 key | 当前步骤页内表格、工具栏、提示条 |
| `modal` | 各 `.modal-dialog` 整体能力 |

弹窗条目在弹窗**未打开**时不显示徽章；打开后隐藏背景步骤徽章，避免编号混乱。
