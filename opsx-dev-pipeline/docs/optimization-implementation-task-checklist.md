# opsx-dev-pipeline 优化实施任务清单

本清单基于 `docs/optimization-implementation-plan.md` 的 v2 方案拆解，按实际落地顺序组织为可执行任务。

使用方式建议：
- 按阶段顺序推进，不建议跳阶段并行重构核心流程
- 每完成一个步骤，补充对应产出与验证结果
- 每个步骤都应具备明确的完成标准，避免“改了一些但未闭环”

---

### Step A3：梳理常见失败场景与恢复动作

#### 任务清单
- [ ] 盘点 Phase 0–6 各阶段的常见失败场景
- [ ] 为每类失败场景定义“现象 / 原因 / 恢复动作 / 是否终止”
- [ ] 区分可自动建议恢复的场景与必须人工判断的场景
- [ ] 标记当前已被脚本覆盖的恢复场景
- [ ] 标记当前仅由文档描述、尚未工程化的恢复场景

#### 建议覆盖场景
- [ ] `openspec` 未安装或不可执行
- [ ] 当前目录不在 git 仓库内
- [ ] change 名不存在

- [ ] schema 探测失败或信息不完整
- [ ] instructions / apply / archive 命令失败
- [ ] verify 命令推导失败
- [ ] 审查后修复回环未闭合
- [ ] 单测未通过但用户希望继续
- [ ] 归档后进入提交/合并阶段时状态不完整

#### 产出物
- 失败场景与恢复动作矩阵

#### 完成标准
- 高频失败场景全部有对应恢复动作
- 能区分哪些失败应直接结束，哪些失败应继续引导恢复

- [x] 定义默认动作的触发条件与禁用条件
- [x] 明确默认动作不能覆盖的高风险场景

### Step B3：优化主路径脚本调用顺序

#### 任务清单
- [x] 盘点主路径中所有重复脚本调用点
- [x] 分析 schema 探测、状态查询、上下文解析的复用机会
- [x] 调整命令执行顺序，减少无必要的重复调用
- [x] 识别可合并的只读检查步骤
- [x] 对“轻量上下文”和“完整上下文”使用场景做区分

#### 当前进展
- 已将 `Phase 0` 的 schema 探测结果定义为后续主路径的首份事实来源，避免在后续 Phase 重复做同类探测
- 已将 `Phase 1` 中的已有 change 续接改为优先复用入口阶段的 `openspec status` 结果，仅在入口结果缺失、制品被修改或需要刷新 `ready` 状态时才重查
- 已将 `Phase 2` 的 `opsx-change-context.sh` 定义为自定义 schema 主路径中的首选上下文快照入口，并要求 `Phase 3 / 5 / 4` 优先复用
- 已将 `Phase 4` 的 verify 解析收敛为 `opsx-resolve-verify.sh` 首选，`opsx-change-context.sh` 仅作上下文回退补充
- 已在相关 Phase 文档中区分“入口判路”“阶段内复核”“上下文快照复用”三类语义，为后续脚本层收敛保留边界

#### 产出物
- 主路径调用优化表
- 调整后的主路径执行顺序说明

#### 完成标准
- 高频路径调用次数下降
