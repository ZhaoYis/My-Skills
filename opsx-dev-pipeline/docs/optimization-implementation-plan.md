# opsx-dev-pipeline 优化实施计划 v2

## 1. 文档定位

本方案用于指导 `opsx-dev-pipeline` skill 的下一阶段优化工作。

与 v1 不同，v2 明确以当前仓库的真实形态为边界进行规划：

- Skill 主入口与执行约束位于 `SKILL.md`
- 主流程由 `references/phase-*.md` 与 `references/recovery-guardrails-appendix.md` 定义
- 自动化能力主要由 `scripts/opsx-*.sh` 提供
- 质量保障以现有 shell 自测与回归脚本为基础

因此，v2 不再以“平台化产品能力”作为近期目标，而是优先优化以下三类问题：

1. 流程稳定性与可恢复性
2. 用户决策负担与执行效率
3. 配置化与可维护性

## 2. 当前现状与主要问题

### 2.1 当前能力边界

当前 skill 已具备以下基础能力：

- 基于 Phase 0–6 的完整需求开发流水线
- 对 OpenSpec 默认 schema 与自定义 schema 的兼容支持
- 基于 shell 脚本的预检、状态获取、制品生成、上下文解析、校验、归档等能力
- 基于 `opsx-selftest.sh` 的基础自测能力

### 2.2 当前主要痛点

结合当前实现，主要问题集中在以下几个方面：

#### A. 决策点较多，用户负担偏高
- 多个 Phase 都包含决策点
- 用户在补充澄清后，容易出现“只解释、不推进流程”的风险
- 某些场景下默认动作不够明确，需要额外确认

#### B. 错误恢复路径虽已定义，但工程化程度不足
- `references/recovery-guardrails-appendix.md` 已定义恢复规则
- 但部分失败场景仍依赖模型临场判断，缺少更强的脚本化支撑
- 用户看到错误后，不一定能立即理解下一步该怎么做

#### C. 脚本能力较完整，但输出一致性和可组合性仍可提升
- 当前脚本已覆盖主要流程节点
- 但不同脚本的输出重点与结构仍有进一步统一空间
- 不利于 skill 在复杂场景下做稳定分支判断

#### D. 测试覆盖已有基础，但仍偏向主路径
- 已具备集成脚本与自测脚本
- 但对中断恢复、异常分支、决策点回环、schema 边界场景的验证仍可加强

## 3. v2 优化目标

v2 聚焦三个核心目标。

### 目标 1：降低中断率，提高流程连续性
通过统一决策点文案、增强恢复指引、补足状态判断依据，减少流程卡住、跳步或误终止。

### 目标 2：减少用户决策疲劳，提高执行效率
通过收敛决策点、引入可解释默认动作、减少重复确认，降低每次流水线推进所需的交互成本。

### 目标 3：增强工程可维护性
通过脚本输出标准化、测试补强、轻量配置化，提升后续迭代效率与质量稳定性。

## 4. 优化原则

### 4.1 先稳再快
优先保证 Phase 流程判断准确、恢复路径清晰、自测稳定，再考虑进一步提速。

### 4.2 优先改造现有资产
优先修改 `SKILL.md`、`references/` 和 `scripts/`，尽量不引入新的复杂运行时依赖。

### 4.3 只做轻量配置化
近期只支持项目级、技能级的轻量配置，不引入插件系统、仪表板平台、复杂持久化状态管理。

### 4.4 以可验证为前提
每项优化都应能通过脚本测试、回归用例或明确的流程演练进行验证。

## 5. 分阶段实施方案

**实施项**：

### 5.2 错误恢复与护栏补强
**目标**：让常见失败场景更容易恢复，而不是停在报错解释。

**实施项**：
- [ ] 梳理 Phase 0–6 常见失败场景与标准恢复动作

- 不在 git 仓库中
- change 不存在或状态不一致

**优先处理脚本**：

- `scripts/opsx-detect-schema.sh`
- `scripts/opsx-change-status.sh`
- `scripts/opsx-change-context.sh`

- `scripts/opsx-validate-change.sh`

### 5.4 测试补强：恢复与边界场景
**目标**：将关键恢复路径纳入自动化回归。

**实施项**：

- [x] 为决策点回环补充流程级测试（以可执行代理场景落地）

### 6.1 决策点收敛与默认动作优化
**目标**：减少无价值确认，提高推进效率。

**实施项**：
- [x] 识别必须由用户确认的决策点与可自动默认的决策点
- [x] 为高频路径定义可解释默认动作
- [ ] 减少重复询问同一类信息
- [ ] 优化已有 change 续接时的推荐动作排序

**当前进展**：
- 已在 `references/recovery-guardrails-appendix.md` 建立 A/B/C 决策自动化分级
- 已明确“推荐默认”与“自动默认”的区别，并补充默认动作触发条件与禁用条件
- 已对齐高风险 Phase 文档，明确跳过审查、跳过单测、未完成项归档、敏感文件、verify 不确定、merge conflict 等场景不得默认

**优化方向**：
- 对“显然应继续当前 Phase”的场景优先推荐继续
- 对“已有明确上下文”的场景避免重复总结后再追问
- 对“仅需局部补充”的情况尽量一次性收集缺口

### 6.2 流程执行顺序优化
**目标**：减少冗余命令调用与重复上下文拼装。

**实施项**：
- [x] 分析 Phase 1–6 中可合并的脚本调用
- [x] 避免重复执行状态查询与 schema 探测
- [x] 对只读类检查步骤做最小化调用优化
- [x] 明确哪些场景需要完整上下文，哪些场景可用轻量上下文

**当前进展**：

### 6.3 面向用户的提示优化
**目标**：让每一步更易理解，降低新用户学习成本。

## 第三阶段：轻量配置化与可维护性建设（中优先级）

### 7.1 轻量配置化
**目标**：提高适配不同项目的能力，但不引入复杂平台化设计。

**实施项**：
- [x] 识别适合配置化的稳定参数
- [ ] 支持少量项目级默认行为配置
- [ ] 支持部分默认提示语或推荐动作的配置化
- [ ] 明确配置优先级与回退规则

**当前进展（Step C1 已完成）**：
- 已将现有规则分为两类：
  - **稳定参数**：跨项目会变化、但变化模式稳定，且只影响低风险默认或呈现层偏好
  - **流程硬约束**：定义 Phase 主干、门禁、恢复护栏与结构化脚本契约的核心规则，不允许被项目配置覆盖
- 已明确 Step C1 仅负责“配置化边界识别”，不涉及配置文件格式、读取位置、优先级、缺失回退或非法值降级；这些内容留给 Step C2
- 已将后续可进入设计的最小配置项集合收敛为 4 类，避免把流程裁决逻辑错误下放给配置

**建议配置范围（最小集合）**：
- 默认推荐动作顺序（`default_recommended_action_order`）
- 提示语展示偏好（`prompt_toggles`）
- verify 命令偏好（`verify_command_preference`）
- schema 补充规则（`schema_supplement_rules`）

**配置化边界说明**：
- 上述候选项仅允许影响“推荐顺序、展示层偏好、低风险 fallback 偏好、非冲突型 schema 补充规则”
- 候选项不得改变任何 Phase 主干顺序、决策点确认等级、恢复优先级或门禁条件
- `verify_command_preference` 只能在既有 verify 候选之间表达项目偏好，不得取消“archive 前必须完成 verify 解析/确认”的要求
- `schema_supplement_rules` 只允许做加法型、非冲突型补充，不得推翻 skill 已有的流程编排、错误处理与脚本输出契约

**明确不纳入配置范围的硬约束**：
- Phase 0–6 主干顺序与阶段切换条件
- 提案确认、代码审查、单测、verify、归档、提交/推送/合并等门禁
- A / B / C 决策点分级与显式确认要求
- 暂停 / 恢复 / 终止的语义边界
- 保守恢复、回到更早阶段、状态冲突时的裁决规则
- 关键脚本的结构化输出契约（如 `status` / `reason` / `nextAction`）

**Step C1 与 Step C2 的边界**：
- Step C1：识别“什么可以配、什么不能配、最小可配集合是什么”
- Step C2：再设计配置读取位置、格式、默认值、覆盖优先级与非法配置的降级策略

**建议配置范围**：
- 默认推荐动作顺序
- 是否优先展示某类说明
- 常用 verify 命令偏好
- schema 相关补充规则

### 7.2 维护性提升
**目标**：降低后续升级 `SKILL.md`、`references/` 与脚本时的联动成本。

**实施项**：
- [ ] 建立文档与脚本字段映射表
- [ ] 补充关键脚本的输入 / 输出约定说明
- [ ] 收敛重复描述，减少多处手动同步成本
- [ ] 识别可抽取的公共逻辑，避免脚本间规则漂移

### 7.3 回归基线建设
**目标**：为后续持续优化提供稳定基线。

**实施项**：
- [ ] 建立优化前后的流程对比样例
- [ ] 固化高频使用场景回归集
- [ ] 为后续版本迭代预留基线指标

**预期周期**：2 周

## 6. 暂不纳入 v2 的事项

以下方向有价值，但不纳入当前 v2 范围：

- 独立前端可视化组件
- 流程仪表板
- 插件化架构与第三方扩展 API
- 容器化执行平台
- 跨会话“记住我的选择”状态系统
- 通用撤销机制

原因：这些能力需要新的宿主系统、状态管理或平台支持，超出当前 skill 仓库的现实边界。

## 7. 评估指标（v2 版）

v2 使用可工程验证的指标，而不是平台运营型指标。

### 7.1 稳定性指标
- 主路径自测通过率达到 100%
- 新增恢复场景自动化覆盖数 ≥ 8 个
- 关键脚本输出结构一致性达成并完成校验
- 常见失败场景具备明确恢复动作覆盖率 ≥ 90%

### 7.2 效率指标
- 主路径平均额外确认次数减少 ≥ 30%
- 已有 change 续接场景的重复状态查询减少 ≥ 30%
- 高频流程的脚本调用次数减少 ≥ 20%

### 7.3 可维护性指标
- 关键脚本输入输出约定文档覆盖率达到 100%
- `SKILL.md` 与 `references/` 的决策点文案差异显著减少
- 新增优化项均具备至少一种自动化验证方式

## 8. 测试与验收策略

### 8.1 测试层次
- 脚本级测试：验证单个 `opsx-*.sh` 的输出与错误处理
- 流程级测试：验证 Phase 串联主路径与异常分支
- 边界场景测试：验证 schema、stacks、恢复、暂停续接等特殊情况

### 8.2 验收原则
每个优化项在合入前至少满足以下之一：
- 可由现有或新增脚本自动化验证
- 可通过明确的流程演练步骤复现与验收
- 有对应的失败前 / 修复后对比结果

## 9. 建议排期

| 阶段 | 名称 | 周期 | 目标 |
|------|------|------|------|
| Phase A | 稳定性与恢复优化 | 2–3 周 | 降低中断、补强恢复、统一脚本输出 |
| Phase B | 效率与交互收敛 | 2–3 周 | 减少决策负担、优化主路径推进效率 |
| Phase C | 轻量配置化与维护性 | 2 周 | 提升适配性、降低后续维护成本 |

总周期建议：**6–8 周**。

## 10. 风险与缓解措施

### 风险 1：优化过程中破坏既有主路径
**缓解**：每次修改后执行主路径回归与自测，不在一个提交中同时重写多类核心规则。

### 风险 2：文案与脚本规则不同步
**缓解**：优先统一关键决策点文案，并为脚本输出建立字段约定，减少隐式依赖。

### 风险 3：配置化过早扩大复杂度
**缓解**：仅做轻量配置化，严格限制配置范围，不引入插件化或持久化状态系统。

### 风险 4：恢复规则增加后反而引起分支膨胀
**缓解**：优先覆盖高频失败场景，低频场景继续保持人工判断，不一次性穷举全部分支。

## 11. 成功标准

v2 完成后，应达到以下结果：

1. 用户在主路径上的中断率明显下降
2. 澄清后能更稳定地回到正确 Phase 推进流程
3. 常见失败场景具备更明确、可执行的恢复动作
4. 关键脚本输出更稳定，便于 skill 做一致判断
5. 主路径与边界场景回归覆盖显著增强
6. 后续继续迭代时，修改成本和联动风险下降

## 12. 下一步落地建议

建议按以下顺序启动实施：

1. 先梳理并统一决策点文案与恢复规则
2. 再统一关键脚本的输出结构
3. 随后补强自测与异常路径回归
4. 最后再做轻量配置化

这样可以确保 v2 优化首先解决“能否稳定推进”的问题，再处理“是否更快、更灵活”的问题。
