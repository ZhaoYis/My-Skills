## Context

当前贪吃蛇游戏为单文件架构（`index.html`，~5500 行），包含完整的游戏引擎、渲染系统、设置系统、皮肤系统和 AI 挂机模式。地图为全屏动态网格（`COLS × ROWS`），由 `calcGrid()` 根据视口动态计算，但地图本身仅由"背景 + 可选网格线"构成，没有任何静态地形元素。

现有占用检测分散在多个函数中：`snakeOccupies()`、`cellIsOccupiedByBomb()`、食物位置比较。障碍物系统需要新增 `obstacles` 数组和 `cellIsOccupiedByObstacle()` 函数，并在所有占用检测点插入障碍排除逻辑。

**约束**：
- 单文件架构，所有改动集中在 `index.html`
- 必须兼容挂机 AI 模式（AI 的 `floodFillCount` 与 `getAIDirection` 必须感知障碍）
- 障碍物数量随网格面积变化（625~9600 格），需使用面积比例公式 + 上下限

**利益相关者**：玩家（游戏体验）、挂机 AI（寻路正确性）

## Goals / Non-Goals

**Goals:**

- 每局游戏在地图上随机生成一组静态障碍物，增加空间规划挑战
- 障碍物与现有难度体系联动（简单模式无障碍，困难模式障碍更多）
- 提供设置开关，允许玩家关闭障碍物
- 障碍物生成后必须保证蛇出生点、食物、炸弹可达（连通性校验）
- 障碍物参与碰撞、AI 寻路、食物/炸弹生成排除等所有占用检测
- 渲染与现有皮肤系统联动，每个皮肤提供障碍物配色

**Non-Goals:**

- 可破坏/可移动的障碍物
- 预设手绘关卡布局（本期仅随机生成）
- 障碍物与炸弹的交互（如炸弹炸毁障碍）
- 障碍物对分数/速度的影响
- 多人联机模式下的障碍物同步

## Decisions

### 1. 障碍物生成时机：`initGame()` 中一次性生成，整局不变

**选择**：每局游戏初始化时一次性生成所有障碍物，整局保持不变。

**理由**：
- 与炸弹的"动态生成"形成互补，降低实现复杂度
- 玩家可记忆布局，增加策略性
- 避免运行时生成带来的性能开销和连通性校验复杂性

**替代方案**：
- 动态生成（类似炸弹）：增加复杂度，且与炸弹功能重叠
- 预设关卡布局：需要大量美术资源和适配不同网格尺寸的缩放逻辑，工作量大

### 2. 障碍物数量公式：面积比例 + 难度系数

**选择**：
- 简单模式：`obstacleBase = 0`（无障碍）
- 普通模式：`count = max(1, floor(totalCells / 800))`
- 困难模式：`count = max(2, floor(totalCells / 500))`
- 上限：不超过总格数的 15%

**理由**：
- 与 `calcFoodCount()`、`calcMaxBombs()` 风格一致
- 大屏不会过密，小屏不会过稀
- 15% 上限防止极端情况下地图被堵死

**替代方案**：
- 固定数量（如普通 5 个、困难 10 个）：大屏障碍过稀，小屏障碍过密
- 按周长比例：不如面积比例直观

### 3. 碰撞行为：撞障碍 = 撞墙 = 即死

**选择**：蛇头进入障碍格时触发 `gameOver(false, 'obstacle')`，与撞墙同级。护盾可抵挡（消耗护盾，方向反转）。

**理由**：
- 规则简单直观，与现有碰撞体系一致
- 护盾交互与撞墙一致，无需额外逻辑

**替代方案**：
- 扣段（类似休眠炸弹）：增加复杂度，且与炸弹功能重叠
- 减速：增加复杂度，且影响游戏节奏

### 4. 连通性校验：floodFill 从蛇头出发，要求可达 ≥60% 非障碍格

**选择**：生成障碍物后，使用 floodFill 从蛇头出发计算可达格数，要求至少 60% 的非障碍格可达。不通过则重新生成（最多 5 次），之后减少数量重试。

**理由**：
- 复用现有 `floodFillCount()` 逻辑，扩展为同时排除障碍格
- 60% 阈值保证不会把地图切碎
- 重试上限防止死循环

**替代方案**：
- 100% 可达：过于严格，可能限制障碍物布局多样性
- 不校验：可能导致地图被堵死，玩家无法玩

### 5. 设置开关：新增 `showObstacles` 字段，默认 `true`

**选择**：在 `DEFAULT_SETTINGS` 中新增 `showObstacles: true`，设置面板"🎮 游戏"分区新增"障碍物"开关，与"网格线"开关并列。开关仅新局生效。

**理由**：
- 与 `showGridLines` 模式对齐
- 用户可关闭障碍物，适应不同偏好
- 当局不随开关变化，避免运行时状态复杂化

**替代方案**：
- 当局立即生效：需要运行时重新生成障碍物，增加复杂度
- 难度联动（不可关闭）：用户无法选择，体验差

### 6. 渲染层级：网格线 → 障碍物 → 食物 → 炸弹 → 爆炸 → 蛇

**选择**：障碍物渲染位于网格线之后、食物之前。

**理由**：
- 障碍物作为"地形"应在食物/蛇之下，避免遮挡关键元素
- 与现有渲染层级一致（背景 → 网格线 → 食物 → 炸弹 → 蛇）

**替代方案**：
- 障碍物在最上层：遮挡食物和蛇，影响可视性
- 障碍物在背景层：无法区分障碍物和背景

### 7. AI 适配：障碍格视为不可通行，与墙同级

**选择**：AI 的 `getAIDirection()` 候选方向排除障碍格；`floodFillCount()` 将障碍视为不可通行。

**理由**：
- AI 必须能正确绕开障碍，否则挂机模式会莽死
- 与墙的判定一致，无需额外逻辑

**替代方案**：
- AI 可以穿过障碍：违反游戏规则
- AI 特殊处理障碍：增加复杂度，且与墙的判定不一致

## Risks / Trade-offs

**[风险] 障碍物数量公式的系数（800/500）需实测调优**
→ **缓解**：预留参数调整灵活性；实际测试后微调

**[风险] 连通性校验 60% 阈值是否合理**
→ **缓解**：实测后调整；极端情况下降级为无障碍

**[风险] 大屏（96×54=5184 格）障碍物数量可能过多**
→ **缓解**：上限 15% 格子（~777 个）；实测后调整

**[风险] 障碍物与炸弹爆炸的交互**
→ **缓解**：本期障碍物不可被炸毁；后续可考虑

**[权衡] 障碍物整局不变 vs 动态生成**
→ **接受**：整局不变降低复杂度，但减少动态性；本期选择简单性

**[权衡] 60% 连通性阈值 vs 100% 可达**
→ **接受**：60% 允许更丰富的障碍物布局，但可能导致部分区域不可达；100% 过于严格

## Migration Plan

**部署步骤**：
1. 合并 feature 分支到 main
2. 部署静态文件到服务器（单一 HTML 文件直接替换）

**回滚策略**：
- 若出现严重碰撞检测或渲染问题，回滚到上一版本的 `index.html`
- localStorage 新增字段向后兼容，无需数据迁移

**发布验证**：
- 打开页面，选择普通难度开始游戏，确认障碍物生成、碰撞、渲染正常
- 切换简单/困难难度，确认障碍物数量符合预期
- 关闭设置中的"障碍物"开关，确认新局无障碍
- 开启挂机模式，确认 AI 能正确绕开障碍
