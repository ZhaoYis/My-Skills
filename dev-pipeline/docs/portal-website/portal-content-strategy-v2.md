## 零、v2 变更总览

### 0.1 叙事升级路线

```
v1: "让 AI 写出符合团队规范的代码"          → 建立门禁体系
v2: "让 AI 的每一次变更都经得起质疑，也经得起追溯" → 门禁体系 + 对抗验证 + 全链路追溯
```

v1 的核心命题是"约束"——告诉 AI 什么不能做。v2 的命题升级为"验证"——不仅约束 AI，还通过独立子Agent 交叉验证 AI 的产出（经得起质疑），通过状态元数据让每次变更都有完整身份链（经得起追溯）。

### 0.2 新增核心能力（vs v1）

| v1 | v2 |
|---|---|
| 模型直接调用脚本，门禁靠 prompt 约束 | **Hermes 编排引擎**：`hermes advance` 驱动流程，三层防御 |

## 一、目标用户画像 & 核心价值陈述（小幅更新）

### 🎯 首要用户：技术负责人 / Engineering Manager

> 团队在用 AI 编程工具提效，但你发现 AI 的代码跳过测试、忽略规范、甚至提交了密钥文件。你需要在"速度"和"质量"之间建立可控的平衡。

**核心价值 v2：一套智能编排的门禁体系——让 AI 在规范内工作，每次变更由独立Agent 交叉验证，完整链路可追溯、可审计、可回滚。**

关键升级点：
- "门禁体系" → "智能编排的门禁体系"（Hermes 不只是门禁，还编排流程）
- 新增"独立Agent 交叉验证"（子Agent 对抗验证是 v2 的核心差异化）
- "可审查" → "可审计"（元数据增强让审查变审计）

### 次要用户（保持不变）

| 用户 | 一句话价值 |

### 副标题（v2）

> opsx-dev-pipeline 是一个开源的 AI 研发流水线 CLI——为团队初始化完整的提案→实施→审查→测试→归档→交付门禁体系，内置 Hermes 智能编排引擎与子Agent 对抗验证，让 Claude Code、Cursor 或 Codex 在你的规则下工作，每次变更由独立 Agent 交叉验证，不留盲区。

### 替代短版（v2）

> 给团队的 AI 编程助手装上规范、门禁和智能编排。30 秒初始化，7 阶段护航，独立 Agent 对抗验证。

### 竞品定位：AI Agent 失控的对立面（v2 更新）

> AI Agent 越来越自主——它能自己写代码、自己调试、自己部署。速度前所未有的快，但问题也来了：**Agent 做的决策你来不及 review，Agent 之间的交互你根本看不到，三个月前的变更没有一条完整的决策链**。
>
> opsx-dev-pipeline 不是要阻止 AI Agent 的速度，而是要求 Agent **先写提案、通过门禁、接受独立审查、留下记录**，才能合并。它让 Agent 在护栏内自主，而不是在黑暗中自主。

## 三、"之前 vs 之后"叙事（小幅更新）

### 之前：AI Agent 失控（v2 更新）

```
AI Agent 越来越自主 →
  → 团队成员给 Agent 一句指令，Agent 自己写代码、调试、部署
  → 速度太快，没人有时间 review 每一步
  → Agent 跳过了测试，Agent 没说为什么要改那个模块
  → 代码合并了，但三个月后没人知道当初为什么这样写
  → 另一个 Agent 把 .env 也提交了，安全扫描没拦住
  → 你说"下次设个规则"→ 下次换了个 Agent，规则没用上
```

### 有了 opsx-dev-pipeline 后（v2 更新）

```
npx opsx-dev-pipeline init --tool claude --stack backend --yes
  ↓
/opsx-dev-pipeline "给 Todo 加个 dueDate 字段"
  ↓
Hermes 编排引擎接管流程：

  Phase 0  预检：环境就绪，依赖齐全  ✅
  Phase 1  提案：AI 自动写 proposal + specs + tasks，你确认  ✅
  Phase 2  实施：AI 按 tasks.md 逐条实现
  Phase 3  审查：独立子Agent 盲审代码
             ├─ 安全维度：发现 dueDate 未做输入校验，存在注入风险  ❌
             ├─ 正确性维度：时区处理缺失，跨时区场景会出错  ❌
             └─ 规范维度：通过  ✅
             → 2 个 finding，主Agent 确认后回退到 Phase 2 修复
  Phase 2' 修复：AI 补上输入校验 + 时区处理  ✅
  Phase 3' 重审：子Agent 重新审查，3 个维度全部通过  ✅
  Phase 4  单测：主Agent 写测试，子Agent 审查测试覆盖
             ├─ 子Agent：未覆盖"dueDate 在过去"的边界情况  ❌
             → 主Agent 补充该测试用例  ✅
             → 子Agent 复审通过  ✅
  Phase 5  归档：delta spec 合并到主规范，变更永不失忆
  Phase 6  交付：敏感文件扫描 → 提交 → 推送 → 合并 → 打标签
  ↓
变更上线。Who → When → Where → Why → What → How → Review → Test
完整链路永久可追溯。2 次被拦住，2 次修复，0 次侥幸通过。
```

**关键：这不是一个"完美通过"的故事——这是一个"被拦住两次，修复两次，最终安全上线"的故事。产品的价值不在顺畅的时候，在 AI 差点犯错但被拦住的时候。**

### Section 3 — How It Works（更新：Hermes 编排可视化）

**形式：CSS 动画 / 交互式时间线**

```
┌─────────────────────────────────────────────────────────────────┐
│  Hermes 编排引擎                                                │
│  ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌────────────┐  │
│  │ advance  │ → │checkpoint│ → │ decide   │ → │  advance   │  │
│  │ 推进流程  │   │ 决策点    │   │ 用户选择  │   │  继续推进   │  │
│  └──────────┘   └──────────┘   └──────────┘   └────────────┘  │
│                        ↑ 门禁校验（自动）                        │
│                        ├─ proposal 已批准？                      │
│                        ├─ 审查已通过？                           │
│                        ├─ 测试已执行？                           │
│                        └─ 归档已完成？                           │
└─────────────────────────────────────────────────────────────────┘
```

**Hermes 是什么（一句话）：** 一个薄壳编排层——它不复制流水线逻辑，而是确保模型在每个阶段做正确的事、通过正确的门禁、在正确的决策点停下来等你确认。

### Section 5 — Adversarial Review（新增板块）

**标题：AI 写的代码，由另一个 AI 独立审查。**

**问题陈述：**

AI 写代码很快，但它审查自己的代码时存在天然的确认偏差（confirmation bias）——它倾向于认可自己写的东西，忽略边界情况，漏掉安全隐患。

opsx-dev-pipeline v2 的解决方案：**子Agent 对抗验证**。

**三条铁律：**

| 原则 | 含义 |
|---|---|
| **盲审 (Blind Review)** | 子Agent 只收到 raw diff + 项目规范原文，不收到主Agent 的任何评价 |
| **独立身份 (Independent Identity)** | 提示词明确 "You did NOT write this code. The author is someone else." |
| **结构化输出 (Structured Output)** | 子Agent 返回 JSON findings，主Agent 可以验证但不能软处理或删除 |

**两种策略：**

```
策略 A（默认）— 单Agent 综合审查
  主Agent 写代码 → 1 个子Agent 盲审（正确性/安全/性能/可维护性/规范一致性）
  → 有争议 → 升级到第二个独立子Agent 裁决
  → 两个子Agent 意见一致 → 按有问题处理，主Agent 不得推翻

策略 B（高风险触发）— 3Agent 并行审查
  认证/授权/支付/敏感数据/加密领域 → 3 个子Agent 并行：
    子Agent 1: 安全审计
    子Agent 2: 正确性审查
    子Agent 3: 规范审查
  → 投票机制：≥2 票认为有问题 → 按有问题处理
```

**争议裁决流程：**

```
子Agent 发现 finding → 主Agent 验证
  ├─ 可自动验证（硬编码密钥、空指针等）→ 主Agent 读代码确认事实
  └─ 需判断（设计问题、race condition）→ 升级到第二个子Agent
       ├─ 两个子Agent 一致 → 按有问题处理
       └─ 两个子Agent 不一致 → 标记为"需人工判断"
```

**Phase 4 测试审查：**

不只是 Phase 3 有对抗验证。Phase 4 中，主Agent 先利用实现细节知识编写测试，然后**子Agent 审查测试充分性**——输出"未覆盖场景清单"，主Agent 据此补充测试。不是"AI 写的测试 AI 自己看"，而是"写测试的人"和"审测试的人"是不同 Agent。

**适用工具：** 子Agent 对抗验证利用了 Claude Code 的 Agent tool 实现独立上下文隔离，这是目前唯一能原生支持该能力的工具。Cursor 和 Codex 在 Phase 3/4 中采用直接审查模式——同样执行完整的安全/正确性/规范三维度检查，区别在于审查 Agent 与实施 Agent 共享上下文。两者的审查结果都在报告中明确标注审查模式，你可以据此判断是否需要额外的人工 review。

> 三种工具在 opsx-dev-pipeline 中都是平等的第一公民。Claude Code 因其 Agent 架构天然支持对抗验证，如果你追求最强的审查保障，推荐使用 Claude Code。

**为什么这很重要：**

> 传统 AI 编程中，同一个模型写代码、审查代码、写测试、审测试。这不是审查——这是橡皮图章。子Agent 对抗验证是该问题的工程级解决方案。

### Section 6 — Spec-Driven（更新：混合执行模式）

原 v1 的 Prompt-Driven vs Spec-Driven 对比表保留，新增：

**标题：规范驱动 + 灵活执行。你的流程，你的节奏。**

**混合执行模式：**

opsx-dev-pipeline v2 支持三种执行模式，适应不同的团队习惯：

| 模式 | 行为 | 适用场景 |
|---|---|---|
| **Pipeline** | 全程由 `/opsx-dev-pipeline` 命令驱动，Hermes 编排每个阶段 | 正式功能开发，完整门禁流程 |
| **Standalone** | 使用独立命令 (`/opsx:propose`、`/opsx:apply`) 按需执行单个阶段 | 快速迭代、小修小补 |
| **Hybrid** | 混合使用——部分阶段用独立命令，部分用 pipeline 命令 | 灵活切换，状态自动对齐 |

**关键设计：** 无论你从哪个入口进入，状态文件都在 `.pipeline-state/` 下统一管理。独立命令执行后自动记录 phaseHistory，pipeline 恢复时通过 Gate 补偿策略（推断/重检/确认）自动对齐状态——不需要从头开始。

### Section 9 — Limitations（新增板块）

**标题：诚实的边界——我们做不到什么。**

一个好的验证系统，首先要坦诚自己的边界。以下是我们明确做不到的事：

**子Agent 对抗验证 ≠ 替代人工 code review**

| 子Agent 能做的 | 子Agent 做不到的 |
|---|---|
| 发现硬编码密钥、空指针、注入风险等可自动检测的问题 | 理解业务逻辑是否正确（"这个折扣计算策略对吗？"） |
| 检查代码是否符合项目规范（命名、结构、依赖规则） | 判断架构设计是否合理（"这个抽象层有意义吗？"） |
| 验证测试是否覆盖了边界情况 | 评估产品体验（"这个交互流程用户会困惑吗？"） |
| 交叉验证多维度（安全/正确性/规范）的一致性 | 替代团队协作中的知识传递和共识建立 |

> 子Agent 对抗验证是在人工 review **之前**的自动化交叉验证——它让 AI 先相互挑战，把低级的、可自动检测的问题消灭在人工 review 之前，让人的时间花在真正需要判断力的地方。

**对抗验证不能保证 100% 发现**

- 子Agent 和主Agent 使用类似的底层模型，可能存在共通的盲区
- 复杂逻辑错误（如 race condition 的特定时序）可能被两个 Agent 同时遗漏
- 策略 A（单Agent 审查）增加约 15-30 秒，策略 B（3Agent 并行）增加约 30-60 秒——这是"深度"和"速度"的权衡

**混合模式下的状态边界**

- 极端情况下（手动修改状态文件、跨多个工具交替使用独立命令），状态对齐可能不完美
- 遇到这种情况，Gate 补偿策略会降级为"需人工确认"——不会静默失败，但需要你介入

**适用规模建议**

| 场景 | 推荐度 |
|---|---|
| 中小型功能开发（< 500 行 diff） | ✅ 最佳适配 |
| 大型重构（> 2000 行 diff） | ⚠️ 建议拆分为多个小变更 |
| 一次性脚本/配置修改 | ❌ 过度设计，不建议使用 |
| 紧急 hotfix | ⚠️ 可用但需跳过部分门禁（需手动确认） |

### 子Agent 对抗验证

**Q: 子Agent 对抗验证和普通 AI 审查有什么区别？**

普通 AI 审查是同一个模型审查自己写的代码——存在确认偏差。子Agent 对抗验证启动一个独立 Agent，它有独立的上下文，不知道主Agent 的判断，收到的只是 raw diff 和项目规范原文。它被明确告知"你没有写这些代码，作者是别人，你的任务是找出问题"。这类似于医学中的"第二意见"（second opinion），但被工程化为一个自动化步骤。

---

**Q: 子Agent 对抗验证会拖慢流程吗？**

策略 A（单Agent 审查）增加约 15-30 秒。策略 B（3Agent 并行审查）增加约 30-60 秒。对于高风险领域（认证、支付、加密），这个时间是完全值得的。对于低于 50 行且非高风险的 diff，可以配置跳过审查。

---

**Q: 子Agent 和主Agent 意见不一致怎么办？**

两级处理：① 可自动验证的 finding（硬编码密钥、空指针等）→ 主Agent 读代码确认事实，记录"已确认/未复现"；② 需判断的 finding（设计问题、race condition）→ 自动升级到第二个独立子Agent 做争议裁决。两个子Agent 意见一致 → 按有问题处理，主Agent 不得推翻。

---

**Q: 子Agent 会误报吗？怎么处理误报？**

会。误报是任何自动化审查系统都无法避免的问题，我们选择直面它而不是假装不存在。

常见的误报场景：① 子Agent 不理解项目的特定上下文（如"这个硬编码值是 feature flag 的默认值，不是安全问题"）；② 子Agent 对规范的理解过于机械（如"变量名不符合规范，但这是第三方库的接口要求"）；③ 两个子Agent 同时误判同一个问题（概率较低，但可能发生）。

处理机制：第一层——主Agent 验证时，如果发现 finding 可自动验证且事实不成立，直接标记为"未复现"并记录原因；第二层——争议裁决阶段，如果第二个子Agent 也认为有问题，但你在人工 review 时判断是误报，可以在报告中标记为"已人工排除"；第三层——我们追踪误报率，持续优化审查 prompt 以降低误报。

> 误报的代价是浪费几分钟确认，漏报的代价可能是生产事故。我们的设计偏向"宁可误报，不可漏报"——但给你清晰的路径快速排除误报。

---

### 混合执行模式

**Q: 我用 `/opsx:propose` 写了提案，能用 `/opsx-dev-pipeline` 继续吗？**

可以。这是 v2 的 hybrid 模式。独立命令执行时会自动记录到 `.pipeline-state` 的 `phaseHistory` 中。当你后续触发 `/opsx-dev-pipeline` 时，Hermes 会检测已有状态，通过 Gate 补偿策略自动对齐——不需要从头开始，也不会丢失之前的决策记录。

---

**Q: 混合模式下，如果我跳过了一些门禁怎么办？**

Gate 补偿策略分三级处理：① 可推断的 Gate（如 proposalApproved ——如果有 Phase 2 记录，说明你已隐式批准提案）→ 自动通过；② 需重检的 Gate（如测试状态 ——没有记录就询问你是否已通过）；③ 必须确认的 Gate（如交付方式：merge 还是 push-only）→ 无论如何都会询问你。

---

### Hermes 编排引擎

**Q: Hermes 是什么？和直接跑脚本有什么区别？**

Hermes 是一个薄壳编排引擎。它不复制流水线逻辑，而是确保模型在正确的阶段做正确的事。区别在于：v1 中模型需要"记得"调用 `transition`、`archive` 等命令，门禁的生效依赖模型遵守 prompt 指令。v2 中，模型只需调用 `hermes advance`，Hermes 自动判断下一步做什么、是否需要你的决策、门禁是否通过。三层防御（引导层+粘性层+强制层）将意外绕过的概率降到最低。

---

**Q: Hermes 会阻止我手动操作吗？**

不会。Hermes 设计目标不是阻止故意绕过，而是消除意外绕过。你在终端中手动执行 `git push --force` 不会被阻止——但 Hermes 不会替 AI Agent 执行这个操作。Layer 3 强制层（被调用方内部检查）确保即使 AI 直接调用 `archive.mjs`，也会先检查门禁状态。

### 技术细节

**Q: 状态文件能告诉我谁在什么时候做了什么吗？**

能。v2 的状态文件新增了：① 创建者身份（git config user.name + email）；② 机器环境信息（操作系统、主机名、Node.js 版本）；③ 需求追溯（关联外部需求 ID）；④ 唯一指纹（跨系统去重）；⑤ 阶段耗时（每个 Phase 的开始/结束时间）。完整链路：Who → When → Where → Why → What → How → Review → Test。
