# AI 驱动研发流水线 — 从 Vibe Coding 到规范驱动开发

> **核心立场**：Vibe Coding 本身没问题，问题是缺少流程约束。流水线是"给 Vibe 装上安全带"，不是"别 Vibe 了"。

---

## 1. 背景：为什么需要 AI 研发流水线

### 1.1 开场案例：一个真实翻车现场

> 最近我在做一个 agent 项目的能力增强——需要支持解析扫描件。全程用 Vibe Coding 方式构建，整个过程 AI 一直给我很强的信心，每一次改动都告诉我"没问题"。最后发到 QA 测试，目标问题确实解决了，但其他场景被改坏了。我继续 Vibe，最后成功把更多接口也改坏了。最终放弃分支，重头开始。

**案例复盘：**

- 目标场景解决了 → AI 确实提效了
- 其他场景被改坏了 → AI 只管"点"不管"面"
- 继续 Vibe 继续坏 → 没有门禁的"修复"就是恶性循环
- 放弃分支重来 → 最终成本远大于收益

### 1.2 Vibe Coding 的真实价值

- 降低编码门槛，加速原型验证
- 将开发者从重复性编码中解放出来
- 让"想法到代码"的路径极大缩短

### 1.3 Vibe Coding 的实际问题

- AI 跳过测试、忽略规范、甚至提交密钥文件
- "能跑就行" vs "可维护、可信任" 的张力
- 整个过程太顺滑了——顺滑到你不会主动停下来思考"这个改动会影响哪些地方"
- **核心矛盾**：如何在"速度"和"质量"之间建立可控的平衡？



### 1.4 SDD（Spec-Driven Development）是什么？

- 核心理念：先写规范，再写代码，AI 和人都遵循同一份规范
- 流程：Explorer → Proposal → Specs → Design → Tasks → Apply → Review → Test → Archive → Merge
- 企业级项目为什么需要 SDD：
  - 多人协作需要统一的"真相源"
  - 变更历史可追溯，决策可审计
  - AI 产出可验证、可度量的质量门禁

## 2. 实践：opsx-dev-pipeline 全流程



### 2.1 核心洞察：流水线到底拦住了什么？

回到开场的案例复盘——如果当时用了流水线，拦截点不是在 Phase 3 的代码审查，而是在更靠前的地方：

- **Explore 阶段**：AI 会分析现有代码结构，告诉我"扫描件解析涉及哪些模块、哪些接口依赖这些模块"。我实际根本没做这个分析——我甚至不知道哪些接口共用了解析逻辑。
- **Spec 的 Scenario 编写**：Explore 结论会提醒我"以下 3 个接口也依赖解析模块，需要验证回归"。这时候我自然会补上回归场景。
- **tasks.md 的改动范围**：流水线生成的 tasks.md 会列出每个任务涉及的文件和影响范围。如果当时我看到"改动会影响 4 个接口"而不是"只改 1 个接口"，我根本不会让它直接改。

> **结论：流水线不是靠自动化审查拦住 bug，而是靠结构化的"停下来思考"环节，让人在错误发生之前就看到全景图。**



### 2.2 系统全景

- 三个核心组件：CLI（初始化+流水线） / metrics-server（指标采集） / metrics-website（可视化仪表盘）
- 支持三种 AI 工具：Claude Code / Cursor / Codex
- 覆盖前端（React）和后端（Spring Boot）两种技术栈
- 一行命令初始化：`npx opsx-dev-pipeline init`



### 2.3 AI 辅助迭代全生命周期

- **Explore（需求探索）**：AI 分析现有代码、评估技术方案、输出探索结论
- **Grill-Me（思路拷问）**：从安全、性能、可维护性等维度挑战方案，发现盲区
- **Propose（方案编制）**：AI 生成 proposal + spec + design + tasks 四个制品
- **Apply（研发实施）**：AI 按 tasks.md 逐条实现，自动勾选完成状态
- **Review（代码审查）**：5 维度自审（正确性/安全性/性能/可维护性/规范符合度），最多 3 轮修复
- **Test（测试门禁）**：运行测试，失败自动修复重试
- **Archive（归档）**：Delta Specs 合并到主规范，变更永久记录
- **Delivery（交付）**：commit → push → merge（可选）



### 2.4 两种研发模式对比


| 模式   | 一键式流水线                                | 分步骤独立开发                                                            |
| ---- | ------------------------------------- | ------------------------------------------------------------------ |
| 入口   | `/opsx-dev-pipeline` 一条命令走完 Phase 0-7 | `/opsx:propose` → `/opsx:apply` → `/opsx:verify` → `/opsx:archive` |
| 适合   | 需求明确、标准化功能开发                          | 复杂需求、需要精细控制每个阶段产出                                                  |
| 人工干预 | 决策点确认                                 | 各阶段间可审阅修改                                                          |
| 灵活性  | 低（按固定流程推进）                            | 高（可跳转、可回退）                                                         |

## 3. 原理：流水线如何运作



### 3.1 OpenSpec 简介

- OpenSpec 是什么：规范驱动开发的基础 CLI 工具，管理 spec 的创建、变更、校验和归档
- OpenSpec 与 opsx-dev-pipeline 的关系：
  - OpenSpec = 引擎（核心 spec 管理 + CLI 工具）
  - opsx-dev-pipeline = 整车（8 阶段门禁 + 状态机 + 安全交付 + 指标系统）



### 3.2 流水线状态机设计

- 7 个 Phase（0-6），每个 Phase 有明确的输入、输出、决策点
- 状态持久化：`openspec/.pipeline-state/<changeName>.json`，26 个字段
- 可恢复性设计：任意阶段中断后精确恢复，交叉校验 Git + 文件系统事实
- 安全门禁：敏感文件检测、禁止 force push、重试上限（3 轮）、合并冲突协议



### 3.3 如何定制研发流程

- 技术栈定制：编辑 `openspec/config.yaml` 中的 `context` 和 `rules`
- Phase 行为定制：编辑 `references/` 目录下的 Markdown 文件
- 模板体系：Handlebars 模板引擎，`common/` + `tools/overlay/` 两层结构
- Feature Flag 系统：通过 `--feature` 参数启用可选功能模块
- 多 AI 工具适配器架构：统一抽象层，生成各自原生格式的产物

## 4. 建议 & QA



### 4.1 AI 生成的代码，我们还需要看吗？

- 必须看。AI 是"副驾驶"，人是"机长"
- 流水线提供 5 维度自动审查作为第一道防线，但最终决策权在人
- 建议：Phase 1 提案阶段重点审（方向错了全白干），Phase 3 审查阶段关注关键路径



### 4.2 全栈开发如何操作？

- 当前 `init` 只选一个主栈，但 `config.yaml` 支持多栈配置
- 初始化后再手动添加第二个栈的 schema 和 config
- 实操建议：先选后端栈初始化，再补充前端 schema



### 4.3 需求如何拆分？按功能点还是按一个需求？

- 原则：一个 change 对应一个可独立交付、独立验证的功能单元
- 过大的需求拆成多个 change，每个 change 独立走流水线
- 过小的需求可以合并，但每个 change 的 tasks.md 控制在 5-15 个任务为宜
- 探索阶段（`/opsx:explore`）可以帮助判断合理的拆分粒度



### 4.4 技术落地 FAQ

- 这东西能接到我们现有的 CI/CD 里吗？
- 状态文件如果丢了怎么办？
