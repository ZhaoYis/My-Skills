# Phase 1：识别不明确点

## 目标

在提问之前，先系统性地找出需求里"不明确、不完整或有歧义"的地方，避免提出空泛或重复的问题。

## 执行步骤

1. **通读需求输入**
   - 需求描述 / PRD / issue / 聊天片段 / 业务背景，标出读不懂或需要假设才能继续的位置。

2. **按分类逐项扫描**
   - 打开 `assets/ambiguity-types.md`，对照每一类（交互不明确 / 规则边界 / 数据来源 / 异常场景 / 字段含义歧义 / 覆盖盲区 / 输入无法解析）逐项检查。

3. **复用已有上下文**
   - 检索知识库、README/CLAUDE.md/AGENTS.md、现有实现：能从既有事实确定的，不要列成澄清问题。
   - 只保留"必须由产品/干系人回答"的真正不明确点。

4. **标注关联位置**
   - 每个不明确点记录它出现在需求的哪一段 / 哪个功能，供 Phase 2 生成"关联位置"列。

## 输出要求

- 一份按分类归类的不明确点清单。
- 每个不明确点标注其在需求中的关联位置。

## Guardrails

- 不要把能从现有上下文确定的内容当成不明确点。
- 不要在本阶段直接给出问题措辞（留到 Phase 2 统一规范化）。
- 不猜测意图；不确定就标为不明确点。
