# Phase 2：定位入口与上下文

## 目标

找到本轮学习对象在仓库中的真实入口，并建立足以支撑后续追踪的初始上下文。

## 执行步骤

1. 根据学习入口，在代码、文档、配置、测试、脚本中寻找最直接的落点。
2. 记录入口相关的关键文件，例如：
   - 路由 / handler / controller
   - service / use case / manager
   - schema / DTO / model
   - 配置 / feature flag / 环境变量
   - 设计文档 / README / ADR / 知识文档
   - 验证入口行为的测试
3. 判断入口是否已经足够代表该功能闭环，还是仅是其中一个局部切片。
4. 若存在多个候选入口，列出差异并请用户确认采用哪一个。
5. 建立最小上下文图：谁触发它、它依赖什么、它影响谁。

## 输出要求

至少给出：
- 当前确认的主入口
- 关联的关键文件或文档
- 为什么这些入口与本轮目标相关
- 初始上下文图（上游 / 本体 / 下游）
- 下一步准备追踪的方向

## 判断标准

进入下一阶段前，应满足：
- 已确认一个主入口，而不是一组散乱候选
- 已有足够上下文知道从哪里开始追踪
- 关键候选文档与测试已纳入视野

## Guardrails

- 入口定位优先选择“最靠近用户问题”的位置，不要一开始就跳到过深的底层实现。
- 若仓库已有现成知识文档，必须先纳入上下文，避免重复劳动。
- 若入口很多，不要全部平铺展开；优先选择最能解释行为的一条主链。
- 不要因为技术层次更低就误认为它更适合作为学习入口。
- （可选）做结构性定位（谁调用谁、符号定义在哪、影响面）时，若同级 `opsx-dev-pipeline` 技能已启用 `structural-analysis-hint`（默认关闭，见其 `assets/structural-analysis-hint.md`）且仓库具备结构化检索能力，优先用之；不可用时按文本检索进行并标注盲区。
