# Phase 3：追踪实现链路

## 目标

从入口出发，梳理关键调用链、依赖边界、数据流、状态变化与业务规则来源，形成稳定的“可解释路径”。

## 执行步骤

1. 从主入口向下追踪核心调用链。
2. 记录关键节点：
   - 输入校验 / 参数转换
   - 业务决策点
   - 数据读取 / 写入
   - 配置读取 / 开关判断
   - 外部依赖或三方服务
   - 错误处理与回退逻辑
   - 触发的副作用或异步流程
3. 找出对理解业务真正关键的测试、脚本或文档。
4. 对于不确定的业务意义，明确标注“代码事实”和“待用户确认解释”。
5. 若链路存在明显分支，优先标出主干路径，再补充分支条件。
6. 若发现现有知识与代码不一致，记录为“待修订知识点”。

## 输出要求

至少整理出：
- 主链路步骤
- 关键分支条件
- 关键依赖点
- 涉及的数据对象 / 配置 / 状态
- 已确认的事实
- 待确认的业务解释
- 可能值得沉淀的稳定规则

## 判断标准

进入下一阶段前，应满足：
- 已能用较短篇幅解释“这条功能链路是如何工作的”
- 已识别出影响行为的关键条件，而非只看到函数跳转
- 已区分稳定规则与实现细节

## Guardrails

- 不要求把所有实现细节都写成知识；重点是后续最值得复用的认知。
- 不要把猜测包装成结论。
- 如果链路过深，优先保留能解释行为的关键节点，省略机械性细节。
- 若存在多个实现分支，不要默认它们同等重要；先标记默认路径、异常路径、降级路径。
- 不要只追踪代码调用关系，还要关注配置、数据与文档对行为的约束。
