# Phase 2：按通用章节骨架撰写

## 目标

依据 `assets/section-skeleton.md` 的通用骨架，把上下文证据组织成一份让实现者能直接照做的设计，且**只保留有用的章节**。

## 执行步骤

1. **逐节按需取用骨架**
   - 打开 `assets/section-skeleton.md`，按骨架顺序考虑每一节。
   - 标"仅当有"的章节（接口/契约、数据/存储、流程图、异常场景）只有真实存在时才写；没有就整节删除，不要留空壳。

2. **为每节标注受众**
   - 每节开头标 `[实现者]` / `[前端/调用方]` / `[测试]`，内容只写给标注读者看的信息。
   - 同一信息不要在多个受众章节重复展开。

3. **撰写改动影响汇总表**
   - 套用 `assets/impact-summary-template.md`，按文件级粒度列出受影响项。
   - **必须**单列至少 1 个"不受影响"项，证明已做过边界分析。

4. **撰写复用与风险分析**
   - 列出 Phase 1 盘点到的可复用实现。
   - 对风险按 高 / 中 / 低 分级，并给出应对方向。

5. **撰写验证断言字段**
   - 为每个关键行为给出可验证的断言：断言字段 + 数据来源 + 判定方式（自动 / 人工）。
   - 这部分将被 `opsx-verify` 直接消费，务必具体、可执行。

6. **拆分任务到文件粒度**
   - 每条任务对应一个文件变更；若一条任务需要改多个文件，拆成多条。
   - 命令 / 构建 / 测试以"按项目基准"表述，不写死技术栈。

## 输出要求

- 一份结构清晰、章节均通过相关性判断的设计文档。
- 含改动影响汇总表（带"不受影响"项）。
- 含验证断言字段。
- 含文件级任务清单。

## Guardrails

- 不要为了"格式完整"而保留无用章节。
- 不要把实现细节塞进面向调用方/测试的受众章节。
- 不要在设计里出现具体技术栈命令；统一"按项目基准"。
