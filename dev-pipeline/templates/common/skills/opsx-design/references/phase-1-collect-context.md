# Phase 1：收集上下文

## 目标

在动笔写设计之前，先把"要设计什么、依赖哪些既有事实、受什么基准约束"收集齐，确保设计建立在证据之上而非臆测。

## 执行步骤

1. **确定设计目标与边界**
   - 这次设计覆盖哪个需求 / 能力单元；明确不在本次设计范围内的部分。
   - 若范围过大，先收缩为一个可设计单元。

2. **优先复用已有产出**
   - 若已运行 `opsx-analysis`：直接复用其需求目标、范围、功能点拆解、影响面与待确认问题，不重复梳理。
   - 若有澄清清单（`opsx-clarify`）：把已回答项纳入约束，未回答项标记为"设计待确认"。
   - 检索知识库（`.knowledge/` 或项目既有约定）：复用已沉淀的能力、接口、数据模型、风险与经验。

3. **盘点可复用的现有实现**
   - 现有模块 / 接口 / 数据结构 / 工具函数中，哪些可直接复用或扩展，避免重复造轮子。
   - 记录复用点，供 Phase 2 的"复用与风险分析"章节使用。

4. **读取项目基准**
   - 构建 / 启动 / 测试 / 校验命令一律按项目基准解析：优先 `openspec/config.yaml`，回退 `AGENTS.md` → `CLAUDE.md` → README / 脚本启发式。
   - 不在设计中写死任何具体技术栈命令；以"按项目基准"表述。

## 输出要求

至少形成一份上下文证据包，包含：
- 本次设计目标与范围（做什么 / 不做什么）
- 已复用的分析结果 / 澄清结论 / 知识库条目
- 可复用的现有实现清单
- 项目基准来源（用于后续命令表述）
- 仍待确认的设计问题

## Guardrails

- 缺乏证据时不要直接进入章节撰写；先补齐上下文或显式标记为待确认。
- 不重复 `opsx-analysis` 已经完成的工作；复用而非重做。
- 不引入与目标无关的上下文，避免设计膨胀。
