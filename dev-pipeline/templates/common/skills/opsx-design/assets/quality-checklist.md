# 设计质量自检清单

逐条核对，任一不通过则回到撰写阶段修订。

## 相关性

- [ ] 每个章节都通过"去掉它实现者还能否正确实现？"测试；不能删的才保留。
- [ ] 没有为了格式完整而保留的空壳 / 套话章节。

## 受众

- [ ] 每节都标注了受众：`[实现者]` / `[前端/调用方]` / `[测试]`。
- [ ] 每节内容只写给标注读者，没有把实现细节塞进调用方/测试章节。

## 边界完整性

- [ ] 改动影响汇总表覆盖到文件级粒度。
- [ ] 影响汇总表**至少包含 1 个"不受影响"项**（缺失即视为漏做边界分析）。

## 可实现性

- [ ] 新增接口/契约列出了完整字段；修改只列变更字段。
- [ ] 数据/存储变更（若有）说明了迁移与回滚考虑。
- [ ] 复用与风险分析列出了可复用实现，并对风险做了 高/中/低 分级。

## 可验证性

- [ ] 含验证断言字段：每条 = 断言字段 + 数据来源 + 判定方式（自动/人工）。
- [ ] 验证断言可被 `opsx-verify` 直接消费。

## 任务粒度

- [ ] tasks 每条对应一个文件变更；跨多文件的任务已拆分。

## 通用化

- [ ] 全文无写死技术栈词（如具体构建/测试工具名）。
- [ ] 命令 / 构建 / 测试统一表述为"按项目基准（`openspec/config.yaml` → `AGENTS.md` → `CLAUDE.md`）与既有约定"。
