# Phase 3：冒烟 / 契约 / 数据校验

## 目标

针对 Phase 1 的验证目标，逐条执行功能校验，并按"自动 vs 人工"的判定标准选择合适的验证方式。

## 自动 vs 人工判定标准

- **可自动验证**：纯查询、简单入参、无副作用、结果可程序化断言的目标。
  - 做法：用真实样例输入触发，断言输出与"验证断言字段"一致。
- **需人工验证**：写操作、复杂对象、状态流转、跨系统副作用。
  - 做法：给出人工验证清单，逐项由人确认；从数据源取真实样例、带认证态发起请求，避免用伪造数据掩盖问题。

## 执行步骤

1. **冒烟校验**
   - 先确认主链路能跑通（核心入口可访问、核心流程不报错）。

2. **契约校验**
   - 对接口/命令：核对入参、出参字段、错误码是否与设计契约一致。
   - 新增字段验证存在与类型；修改字段验证变更与兼容性。

3. **数据校验**
   - 从真实数据源取样例（而非编造数据），核对写入/读取/状态流转结果与预期一致。
   - 写操作类用人工清单确认副作用范围与回滚可行性。

4. **逐条对照验证断言字段**
   - 每条断言记录：判定方式（自动/人工）、实际结果、是否通过。

## 输出要求

- 每条验证目标的执行结果（通过 / 不通过 + 证据）。
- 人工验证清单（针对需人工确认的目标）。

## Guardrails

- 不用伪造数据替代真实样例。
- 写操作 / 状态流转不得只靠自动断言草率判定，给出人工确认清单。
- 单条不通过时进入 `assets/pass-criteria.md` 的失败回路。
