# Phase 1：解析验证目标

## 目标

把"这次要验证什么"先确定下来：从变更与设计中提取接口、数据、影响面，形成一份可执行的验证目标清单。

## 执行步骤

1. **定位变更范围**
   - 若给出 change 名：读取 `openspec/changes/<name>/` 下的 `design.md` / `proposal.md` / delta `specs/` / `tasks.md`。
   - 若无 change：基于变更说明与 `git diff`（git 不可用时仅基于设计/说明）确定改动面。

2. **优先复用 opsx-design 的验证断言字段**
   - 若设计中已有"验证断言字段"（断言字段 + 数据来源 + 自动/人工）：直接转成验证目标，不重复推导。
   - 若没有：从接口/数据/行为中提炼可验证断言。

3. **提取验证维度**
   - 接口 / 命令 / 入口：哪些对外契约会被触达。
   - 数据 / 存储 / 状态：哪些数据结构、存储项或状态流转受影响。
   - 影响面：上游调用方与下游依赖中需要回归的部分。

4. **整理为验证目标清单**
   - 套用 `assets/verify-target-template.md`，逐条标注：目标、数据来源、判定方式（自动/人工）、预期结果。

## 输出要求

- 一份验证目标清单，覆盖接口、数据与影响面。
- 每条目标标注数据来源与自动/人工判定。

## Guardrails

- 不要在未确定验证目标前就开始跑命令。
- 不要把不在本次变更范围内的内容纳入验证目标。
- 复用 design 的断言字段，避免重复定义验证项。
