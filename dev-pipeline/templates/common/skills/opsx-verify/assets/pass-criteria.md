# 通过标准 + 失败处理回路

## 通过标准

一次验证判定为通过，需同时满足：

- **构建/启动通过**：构建成功且程序/服务进入可验证状态。
- **功能校验通过**：每条验证目标均有结果，自动项断言成立、人工项已逐条确认。
- **回归通过**：受影响范围的回归无新增失败；未自动化覆盖的影响面已人工确认。
- **证据可追溯**：每条结论都附执行命令 / 数据来源 / 实际结果。

任一不满足 → 整体判定为"未通过"，进入失败回路。

## 失败处理回路

1. **定位**：记录现象——失败的目标、命令、退出码、关键日志片段。
2. **分类**：
   - 构建/启动失败 → 回到 Phase 2。
   - 功能/契约/数据校验失败 → 回到 Phase 3（必要时回 Phase 1 修正验证目标）。
   - 回归失败 → 回到 Phase 4 确认是新引入问题还是既有问题。
3. **修复与重试**：修复后从对应 Phase 重新执行，而不是从头重跑全部。
4. **无法自动判定时**：列出候选/分歧点请用户确认，不擅自下结论。
5. **升级**：多轮仍无法通过时，主动建议缩小验证范围、拆分变更或暂停，由用户决定。

## 与 Pipeline 的边界

- 本清单是"如何判定与如何修复"的能力库。
- `opsx-dev-pipeline` Phase 4 仍是"何时必须验证、是否放行归档"的门禁权威；本 skill 不复制其门禁正文。
