# Phase 2：探索上下文（内置 `opsx-explore` 思路）

## 目标

在正式分析前，先完成一轮探索上下文，形成后续判断所需的“分析证据包”。

## 执行步骤

1. 按优先级搜索相关上下文：
   - 已沉淀知识库（若存在）
   - README / CLAUDE.md / AGENTS.md / docs/ / ADR
   - 与需求最相关的代码入口
   - 测试、配置、脚本中的行为约束
   - 用户补充的业务背景、边界与限制
2. 优先寻找“已有类似能力 / 现有实现 / 现有约定”，不要预设一定要新增。
3. 记录关键证据：
   - 相关文件
   - 现有流程
   - 现有规则
   - 现有边界或约束
4. 若上下文明显不足，整理出需要用户补充的信息，而不是直接推断完整结论。

## 输出要求

至少给出：
- 已探索到的上下文来源
- 与本轮需求最相关的关键证据
- 已有类似实现或相关约定
- 当前仍缺失的信息
- 可进入功能点拆解的依据

## Guardrails

- 这里承担 `opsx-explore` 的职责，但不依赖独立命令。
- 不要只看代码，还要同时看知识、文档、测试、配置和脚本。
- 若现有知识与代码不一致，应显式标记为待确认差异。
- （可选）做结构性探索（调用关系、影响面、符号定义位置）时，若同级 `opsx-dev-pipeline` 技能已启用 `structural-analysis-hint`（默认关闭，见其 `assets/structural-analysis-hint.md`）且仓库具备结构化检索能力，优先用之，文本性问题仍用 grep；不可用时按文本检索进行并标注盲区。
